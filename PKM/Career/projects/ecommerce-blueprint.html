Redis Pub/Sub Real-time stock updates (optional) Redis REALTIME
Why REST over GraphQL?
For a solo dev, REST with OpenAPI is faster to build, easier to debug, and has better tooling. GraphQL is justified only when query shapes are highly variable — eCommerce rarely needs this. Add GraphQL if you build a public API for third-party integrations later.

MONOREPO STRUCTURE

Tooling Choice: Turborepo + pnpm workspaces
Turborepo wins over Nx for its zero-config remote caching, simpler mental model for small teams, and native pnpm support. Turborepo remote cache means a CI build that hasn't changed gets restored in seconds.

CI/CD PIPELINE

Core Principle: Only build what changed
Use dorny/paths-filter to detect which apps changed. Combined with Turborepo remote cache, a PR touching only the storefront never builds or deploys the API. CI time drops from 8min to 90sec.
Pipeline per Environment
PR
Every Pull Request → ci.yml
Spins up Postgres + Redis containers. Runs: type-check → lint → migrate test DB → test with coverage → upload to Codecov.
type-check lint test coverage
STG
Merge to develop → deploy to staging
Affected apps detected. Docker image built and pushed to ECR. Prisma migrations run as a one-off ECS task. ECS service updated. aws ecs wait for stable deployment.
docker build ECR push migrate ECS deploy
PRD
Merge to main → deploy to production
Same steps as staging but with production cluster. Migrations run before service update. Waits for services-stable before marking success.
production zero-downtime
deploy-api.yml — change detection + ECS deploy +
YAML
jobs: changes: outputs: api: ${{ steps.filter.outputs.api }} steps: - uses: dorny/paths-filter@v3 id: filter with: filters: | api: - 'apps/api/**' - 'packages/**' deploy: needs: changes if: needs.changes.outputs.api == 'true' steps: - name: Build and push image run: | docker build -t $ECR_REGISTRY/ecommerce-api:${{ github.sha }} \ -f apps/api/Dockerfile . docker push $ECR_REGISTRY/ecommerce-api:${{ github.sha }} - name: Run migrations (ECS one-off task) run: aws ecs run-task --cluster prod --task-definition api-migrate - name: Deploy new task definition run: aws ecs update-service --cluster prod --service api --force-new-deployment - name: Wait for stable run: aws ecs wait services-stable --cluster prod --services api

GIT WORKFLOW

Strategy: Modified Gitflow (not pure trunk-based)
Pure trunk-based development requires mature feature flag infrastructure. For a solo dev shipping Stripe payment flows, the develop buffer branch prevents half-done features from reaching production. Trunk-based becomes viable when you have 3+ developers and feature flags wired up.
Branch Model
main          ← Production. Protected. Linear history only.
  │
  └── develop ← Staging. Integration branch. CI gate.
        │
        ├── feature/cart-persistence
        ├── feature/stripe-webhooks
        ├── fix/order-total-rounding
        └── hotfix/payment-timeout   ← branches FROM main, merges TO main + develop
Branch Protection Rules
  • ✓Require PR — no direct pushes to main or develop
  • ✓Required status checks: ci / Lint, Type-check, Test must pass
  • ✓Require linear history (rebase only, no merge commits)
  • ✓No force pushes, ever
  • ✓Conventional commits enforced via commitlint in CI
Conventional Commits
BASH
# Format: type(scope): description feat(orders): add order cancellation endpoint fix(payments): handle Stripe idempotency key collision chore(deps): upgrade Prisma to 5.x refactor(auth): extract token rotation into separate service perf(products): add missing index on categoryId column
Versioning: Changesets
BASH
pnpm changeset # Describe what changed pnpm changeset version # Bump package versions pnpm changeset publish # Publish shared packages if needed

SECURITY

Auth Best Practices
  • ✓bcrypt passwords, salt rounds ≥ 12
  • ✓Access tokens: 15min expiry
  • ✓Refresh tokens: 7d, HttpOnly cookie
  • ✓Token rotation on every refresh
  • ✓Redis JTI blocklist for logged-out tokens
  • ✓OAuth links to existing email if match
Secrets Management
  • ✓.env.local (gitignored) for local dev
  • ✓AWS Secrets Manager → ECS env vars
  • ✓GitHub Secrets for CI/CD
  • ✓Zod env validation on startup
  • ✓Never log secrets (Sentry scrubbing)

PERFORMANCE & SCALING

Scaling Phases
P1
0 – 10k orders/month · Single region
ECS Fargate: 2 tasks (1 vCPU, 2GB each). RDS t3.medium, single AZ. ElastiCache t3.micro. Storefront on Vercel (free tier handles traffic bursts). Total AWS cost: ~$80/month.
2 ECS tasks RDS t3.medium ~$80/mo
P2
10k – 100k orders/month · Add redundancy
ECS auto-scaling (CPU > 70%). RDS Multi-AZ + read replica for analytics. ElastiCache cluster mode (3 nodes). SQS for all async processing. Estimated cost: ~$300/month.
auto-scale multi-AZ read replica
P3
100k+ orders/month · Optimize
Extract search to Typesense. Analytics to read replica or ClickHouse. PgBouncer for connection pooling. Consider extracting payments service if it becomes a bottleneck.
Typesense ClickHouse PgBouncer
