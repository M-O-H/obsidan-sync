The right engineering mindset

Core principle

Build first, learn in context

Industry standards are not academic rules — they are solutions to real problems engineers encountered at scale. You only truly understand a standard when you have felt the pain it solves. Read just enough to start, then build, then read again to understand why.

Do this

Productive habits

  • Pick one feature, build it end-to-end before moving on
  • Write code as if a senior engineer will review it tomorrow
  • Commit to explaining every line you write
  • Treat your project as a production codebase from day one
  • Research standards after you feel the problem, not before
Avoid these

Common mistakes

  • Tutorial hopping without finishing anything
  • Over-engineering before you have working code
  • Copying patterns without understanding the intent
  • Skipping error handling because "it works locally"
  • Learning auth theory without building an auth system
  • Ignoring code review feedback as optional
Mental model

The two questions to ask always

1. "What breaks if this fails at scale?" — Forces you to think beyond the happy path.

2. "Would I be comfortable if a senior engineer read this code right now?" — If not, stop and improve it before moving forward.

Learning phases

Phase 1

Foundation — code quality & structure

This phase is about developing habits that compound. Skipping it means accumulating technical debt that will slow every subsequent phase.

What to learn

  • SOLID principles and when to apply each
  • Clean code conventions — naming, function size, single responsibility
  • Git workflow: feature branches, conventional commits, PR descriptions
  • Monorepo structure and workspace tooling (Turborepo, pnpm workspaces)
  • TypeScript strictly — strict: true, no any

What to build

  • Set up your NestJS + Next.js monorepo with shared types package
  • Create a consistent folder structure for both apps
  • Configure ESLint, Prettier, Husky pre-commit hooks
  • Write your first feature with meaningful commit history

Industry standard at this phase

Code that any engineer can read without asking questions. Every PR has a clear description. Every commit is atomic and intentional.

Phase 2

Core backend — API, auth, database

This is where most of the real engineering happens. Mistakes here are the hardest to fix later.

What to learn

  • RESTful conventions — resource naming, HTTP verbs, status codes
  • JWT + refresh token rotation, PKCE for OAuth flows
  • Database schema design, migrations, and indexing strategy
  • Repository pattern and service layer separation in NestJS
  • Input validation and DTO design with class-validator
  • Rate limiting, CORS, and helmet security headers

What to build

  • Full auth system: register, login, refresh, logout, token revocation
  • Products API with pagination, filtering, sorting
  • Orders API with state machine transitions (pending → paid → shipped)
  • Guards and decorators for role-based access control

Industry standard at this phase

APIs that behave predictably, fail gracefully with structured errors, and handle edge cases. Auth that cannot be bypassed by a simple token replay.

Phase 3

Frontend integration

The frontend is not just UI — it is a client contract with your API. Treating it as such changes how you approach both sides.

What to learn

  • Next.js App Router — server vs client components, data fetching patterns
  • API client abstraction (React Query or SWR for caching, revalidation)
  • Token handling in middleware — silent refresh, route protection
  • Optimistic UI and error boundaries
  • Form validation mirroring backend DTO rules

What to build

  • Auth flow: login, register, silent token refresh on page load
  • Product listing page with server-side filtering and pagination
  • Cart and checkout with optimistic updates
  • Protected admin routes with middleware-level guards

Industry standard at this phase

A UI that works without a reload, fails gracefully on API errors, and never exposes tokens in localStorage or the DOM.

Phase 4

DevOps & CI/CD

What to learn

  • Docker — multi-stage builds, .dockerignore, environment parity
  • GitHub Actions — lint, test, build, deploy pipeline
  • Environment variable management across environments
  • Database migrations as part of the deployment pipeline
  • Basic Nginx reverse proxy configuration

What to build

  • Dockerfiles for both apps, docker-compose for local dev
  • CI pipeline that blocks merges on failing tests
  • CD pipeline that deploys to staging on merge to main
  • Automated database migration step in deployment

Industry standard at this phase

No manual deployments. Every merge to main triggers a reproducible, automated deploy. No environment-specific code — only environment-specific configuration.

Phase 5

Production readiness

What to learn

  • Structured logging with correlation IDs across requests
  • Health check endpoints and uptime monitoring
  • Error tracking (Sentry or equivalent) and alerting
  • Database connection pooling and query optimization
  • Security audit — OWASP Top 10 checklist
  • Load testing and understanding your system's bottlenecks

What to build

  • Logging middleware that tags every request with a trace ID
  • /health and /ready endpoints with dependency checks
  • Global exception filter with structured error responses
  • Admin dashboard with real order/product metrics

Industry standard at this phase

You can diagnose any production issue from logs alone. Your system degrades gracefully rather than failing completely. You know your system's limits before your users do.

Engineering layers

Key principles

Separate by concern, not by file type. Group feature modules together — auth/, orders/, products/ — not by layer across the whole app.

Shared types and utilities live in a packages/ directory accessible to both apps. Never duplicate type definitions.

Every function does one thing. Every module has a single, clear responsibility. If you struggle to name it, that is a design signal.

Common pitfalls

Putting business logic in controllers. Controllers should only handle HTTP concerns — validation, delegation, and response shaping.

Fat service files that know about the database schema. Services should depend on repositories, not on ORM entities directly.

Circular dependencies between modules, usually caused by poor domain boundary decisions.

Key principles

Short-lived access tokens (15 min), long-lived refresh tokens stored as httpOnly cookies, never in localStorage.

Refresh token rotation on every use. A used refresh token should be invalidated immediately to prevent replay attacks.

RBAC at the guard level — roles stored in the JWT, validated on every protected request without a database call.

Common pitfalls

Storing JWTs in localStorage. XSS can steal them. Use httpOnly cookies for refresh tokens, memory for access tokens.

Not implementing token revocation. A logout should invalidate the server-side refresh token, not just delete the cookie client-side.

Checking permissions in service methods instead of guards. By the time code reaches a service, authorization should already be resolved.

Key principles

Resource-oriented URLs. POST /orders not POST /createOrder. HTTP verbs carry the action — the URL should identify the resource.

Consistent error envelope: always return statusCode, message, error, and optionally details for validation errors.

Versioning from day one. /api/v1/ prefix costs nothing now and saves a painful migration later.

Common pitfalls

Returning 200 with an error body. HTTP status codes exist precisely for this — use them. A failed request is not a 200.

Exposing database IDs directly. Use UUIDs or slugs. Sequential integer IDs leak business information and enable enumeration attacks.

No pagination on list endpoints. Every list endpoint that hits a database needs cursor or offset pagination from the start.

Key principles

Every schema change is a migration file, committed to source control, and run automatically in CI. No manual ALTER TABLE commands in production.

Index on every foreign key and every column that appears in a WHERE or ORDER BY clause on a large table.

Use transactions for operations that must succeed or fail together — e.g. creating an order and decrementing stock must be atomic.

Common pitfalls

N+1 queries. A product listing that fires a separate query per product to get its category is an N+1 problem. Use eager loading or data loaders.

Soft deletes without considering their impact on unique constraints and join performance. Think through the full read path before implementing.

Storing sensitive data unencrypted. Passwords, payment tokens, PII — each has a different appropriate storage strategy.

Key principles

Infrastructure as code. If it is not in a file committed to git, it does not reliably exist. Use docker-compose locally, proper IaC (Terraform, Pulumi) for production.

Twelve-factor app principles: configuration from environment variables, stateless processes, explicit dependencies.

Separate environments — local, staging, production — with identical configuration structure and different values.

Common pitfalls

Environment-specific code branches like if (env === 'production') inside application logic. Behavior should not change between environments, only configuration.

Committing .env files. Use .env.example with placeholder values in the repo and a secrets manager for real values.

Key principles

Every request gets a correlation ID generated at the entry point and attached to every log line it produces — across both NestJS and Next.js.

Log at the right level: DEBUG for development noise, INFO for business events, WARN for recoverable anomalies, ERROR for failures requiring attention.

Metrics on the things that matter: request duration, error rate, database query time, and queue depth if applicable.

Common pitfalls

Logging everything at INFO level. When everything is important, nothing is — and searching through logs becomes painful at scale.

No alerting until after a user reports a problem. Set up alerts on error rate thresholds before go-live, not after the first incident.

Logging PII or tokens in plain text. Treat your logs as potentially accessible and redact sensitive fields before writing.

Repeatable feature workflow

Follow this loop for every feature. Click each step to expand.

1. Build — make it work first

▾

Write the simplest implementation that satisfies the requirements. Do not optimize. Do not abstract prematurely. Working code that you can reason about is more valuable than elegant code that does not exist yet.

  • Write the DTO and validate inputs at the controller
  • Implement the service method with direct, readable logic
  • Write the repository query — raw and obvious
  • Return a consistent response shape

2. Research — understand the standard

▸

Now that you have working code and feel the problem space, research how the industry solves this. Read documentation, well-regarded open-source code, or engineering blog posts from companies that have solved similar problems at scale.

  • Look up the relevant RFC or standard (e.g. RFC 6749 for OAuth)
  • Read NestJS or Next.js official docs for the pattern you just implemented
  • Check if your approach matches what senior engineers recommend

3. Improve — close the gap

▸

Apply what you learned. This is where research becomes real understanding. The goal is not to perfectly match every standard — it is to consciously choose where your implementation differs and know exactly why.

  • Add missing error handling and edge cases
  • Improve naming to match domain language
  • Add security controls you had not considered
  • Write or improve input validation to match your DTO intent

4. Refactor — make it maintainable

▸

Restructure without changing behavior. Extract duplicated logic, rename for clarity, flatten unnecessary nesting, and ensure the code reads like a story — top to bottom, without needing comments to explain what it does.

  • Extract shared logic into utilities or base classes
  • Ensure each function/method has one clear purpose
  • Remove dead code and commented-out blocks
  • Check that modules respect their boundaries

5. Document — leave a clear trail

▸

Documentation is not optional — it is part of the feature. A future engineer (often yourself in three months) will need to understand not just what the code does, but why key decisions were made.

  • Add JSDoc to public service methods and non-obvious utilities
  • Update or add Swagger decorators to your NestJS controllers
  • Write a meaningful PR description covering what changed and why
  • Note any non-obvious constraints or known limitations

Applied to your e-commerce project

NestJS auth module

PassportJS with JWT strategy. Separate auth.service.ts for token logic, users.service.ts for user CRUD. Never mix them.

Access + refresh token pair

Access token: 15 min, in-memory on client. Refresh token: 7 days, httpOnly cookie. Rotation on every POST /auth/refresh.

Token revocation table

Store refresh token hashes in the database. On logout, mark as revoked. On refresh, validate against the store before issuing a new pair.

RBAC guards

Custom @Roles() decorator + RolesGuard. Apply globally with role overrides per route. Roles: CUSTOMER, ADMIN.

Next.js middleware auth

Middleware reads the refresh cookie, calls /auth/refresh silently if the access token is absent or expired, then injects the fresh token into the request.

Rate limiting on auth routes

@nestjs/throttler with stricter limits on /auth/login and /auth/register. Log and alert on repeated failures.

Products module with pagination

Cursor-based pagination on GET /products. Filter by category, price range, and availability. Sort by price and created date. Indexed on all filter columns.

Order state machine

Valid transitions: PENDING → PAID → PROCESSING → SHIPPED → DELIVERED. CANCELLED available from PENDING and PAID only. Enforce in the service layer, not in the database.

Atomic inventory update

Decrement stock and create the order inside a single database transaction. Use optimistic locking or a WHERE stock > 0 guard in the UPDATE query to prevent overselling.

Structured error responses

Global exception filter that catches all errors and returns {"statusCode", "message", "error", "timestamp", "path"}. Never expose stack traces in production.

Next.js product page with SSR

Product detail pages use generateStaticParams for static generation where possible. Cart state managed with Zustand or Context, synchronized to the server on order creation.

Middleware-level route protection

Next.js middleware checks for ADMIN role in the token payload before any admin route renders. Server-side protection, not just client-side redirect.

Admin-only API endpoints

Separate controller prefix /admin/ with @Roles('ADMIN') applied at the controller level. No route-level override possible without explicit intent.

Audit log for admin actions

Every destructive or sensitive action (delete product, update order status, modify user) writes a record: who, what, when, and the before/after values.

Dashboard metrics endpoint

GET /admin/metrics returns daily revenue, order counts by status, and low-stock alerts. Use database aggregation queries — never compute in application memory.

Swagger documentation

Every NestJS controller decorated with @ApiTags, every DTO with @ApiProperty. Admin routes tagged separately and marked as requiring bearer auth. Available at /api/docs.
